## 5. Run a case with Allrun

### What it does
`./Allrun` executes the `Allrun` script in the current case.

In the current controlled cases, the script runs:

1. `blockMesh`
2. `splitMeshRegions -cellZones all`
3. `foamMultiRun`
4. removes previous derived `logs/`
5. `foamLog log.foamMultiRun`
6. creates `buoyant.foam` for post-processing

### Command

```bash
./Allrun
```

**Important:** run it from inside the correct case folder.

---

## 6. Clean a case with Allclean

### What it does
`./Allclean` removes results generated by a previous run and returns the case to a clean state so it can be run again.

### Command

```bash
./Allclean
```

### When to use it
Use it before a run that you want to treat as a **new reproducible run**.

### Caution
Do not run it if you still need local results that have not been backed up.

---

## 7. Clean and rerun a case

### What it does
The `&&` operator runs the second command **only if the first one finishes successfully**.

### Command

```bash
./Allclean && ./Allrun
```

This means:

1. clean;
2. if cleaning succeeds;
3. run the case.

## 8. Run several cases sequentially

### What it does
Parentheses create a **subshell**. Each case enters its own folder, runs there, and when the subshell ends the parent shell is still in the folder from which the block was launched.

Therefore, if you start in `cases_controlled_buoyancy`, **do NOT use `../C6_adaptiveDt` for the second case**. After the first subshell ends, you are already back in `cases_controlled_buoyancy`.

### First go to the correct folder

```bash
cd ~/OpenFOAM/QuickCup_Solidification/cases_controlled_buoyancy
```

### Run B6 → C6 → B7 → C7

```bash
(cd B6_adaptiveDt && ./Allclean && ./Allrun) && \
(cd C6_adaptiveDt && ./Allclean && ./Allrun) && \
(cd B7_outer4 && ./Allclean && ./Allrun) && \
(cd C7_outer4 && ./Allclean && ./Allrun)
```

### If B6 already finished and C6, B7, and C7 remain

```bash
(cd C6_adaptiveDt && ./Allclean && ./Allrun) && \
(cd B7_outer4 && ./Allclean && ./Allrun) && \
(cd C7_outer4 && ./Allclean && ./Allrun)
```

### Why sequential instead of parallel
For project comparisons, it is preferable that cases do not compete for CPU, RAM, or I/O at the same time. This reduces an unnecessary source of variation in computational timing.

## 9. Watch the log while a case is running

`tail -f` shows the last lines of a file and keeps displaying new lines as they are written.

It is especially useful from a **second terminal** while the solver continues running in the first one.

### Example: watch B6


### Stop the live view

```text

```

If `tail -f` is running in a second terminal, this stops **only tail**, not the solver running in the first terminal.

## 11. Check whether a run reached End

### Quick method

```bash
tail -n 20 log.foamMultiRun
```

A completed run should normally show `End` near the end.

### Search explicitly for End

`grep` searches for lines containing a text pattern. `-n` also prints the line number.

```bash
grep -n "^End" log.foamMultiRun
```

If nothing appears, do not automatically assume the run completed correctly: inspect the final lines and search for errors.

---

## 12. Search the log for serious errors

### What it does
`grep -E` lets you search for several patterns at once using an extended expression.

### Command

```bash
grep -nE "FOAM FATAL|Segmentation fault|Floating point|Killed" log.foamMultiRun
```

If it returns no lines, none of those texts were found.

### Search for warnings

```bash
grep -ni "warning" log.foamMultiRun
```

- `-i`: ignore uppercase/lowercase differences.

## 14. Regenerate foamLog output

### What it does
`foamLog` extracts time series from `log.foamMultiRun` for post-processing: residuals, Courant number, continuity, iterations, execution times, and more.

Before regenerating them, it is useful to remove the previous `logs/` folder so old and new derived data are not mixed.

### Safe command from inside the case

```bash
rm -rf logs
foamLog log.foamMultiRun
```

### In one line

```bash
rm -rf logs && foamLog log.foamMultiRun
```

### What `rm -rf logs` means
- `rm`: remove.
- `-r`: remove a directory and its contents recursively.
- `-f`: do not ask for confirmation.

**Caution:** use `pwd` first to verify that you are inside the correct case before using `rm -rf`.

## 18. What Ctrl+C does

`Ctrl+C` sends an interrupt to the process running in **that terminal**.

### If the solver is running in that terminal
It can stop the simulation.

### If you are only watching `tail -f` in a second terminal
It stops only the live `tail` view.

**Practical rule:** before pressing `Ctrl+C`, check which process is active in that terminal window.

## 19. Rules for clean comparisons

1. Clean the case before a run that will be used in a comparison.
2. Do not reuse old `logs/` after generating a new `log.foamMultiRun`.
3. Check the date and size of `log.foamMultiRun` whenever there is doubt.
4. Confirm that the solver reached `End`.
5. Search for `FOAM FATAL`, segmentation faults, floating-point exceptions, and killed processes.
6. When comparing computational cost, avoid running the compared cases at the same time.
7. Change one main numerical variable per test whenever possible.
8. Record every relevant change in `PROJECT_AUDIT_LOG.md` as well.

## NARANJA workflow — synchronize local results before documentation

**NARANJA** is the safety workflow used when the local computer contains simulation results newer than GitHub.

Required order:

1. **Local/PC first.** Preserve and version valid results already present on the computer.
2. **GitHub second.** Integrate remote changes without using `force push`.
3. **Analysis.** Use the synchronized repository as the source of truth for metric extraction.
4. **Documentation last.** Update the Audit Log, README, and Command Manual only after the real results are present on GitHub.

Standard workflow from the repository root:

```bash
git add -A
git commit -m "results: sync local simulation outputs"
git pull --rebase origin main
git push origin main
```

If `git commit` reports `nothing to commit`, continue with `git pull --rebase origin main` and `git push origin main`.

### Important note about `.gitignore`

`git add -A` **does not add newly ignored files**. In this project, calculated time directories and most of `postProcessing/` are deliberately ignored to prevent repository bloat.

If an ignored output is scientifically worth preserving, first choose the useful lightweight subset and then add only that path deliberately (for example via a `.gitignore` exception or, for a one-off case, `git add -f <path>`). Do not force-add all calculated time directories automatically.

### Do not use

Do not use `git push --force` to resolve a non-fast-forward rejection when valid local results exist. Prefer `git pull --rebase` after committing the local changes.


## Synchronizing final run results with Git (NARANJA workflow)

When an OpenFOAM batch is run on the local workstation and versionable outputs must become the new source of truth:

1. Preserve valid local results first.
2. Stage and commit versionable logs/results.
3. Integrate newer remote commits afterward with `git pull --rebase`.
4. Push with `git push`.
5. Only then update audit logs, manuals, or analysis conclusions.

Example:

```bash
git add -A
git commit -m "results: sync remaining local controlled-case data"
git pull --rebase origin main
git push origin main
```

Do not use `force push` merely to resolve an ahead remote. This workflow prevents newer remote documentation from replacing or confusing simulation results that still exist only on the local workstation.

## Validating the `solidificationMeltingSource` diagnostic

The `solidificationMeltingMomentumDiagnostics` block is included in `system/researchDiagnostics` for the controlled V3–V7 cases. It does not change the case physics; it only writes derived fields during solver execution.

After synchronizing:

```bash
cd ~/OpenFOAM/QuickCup_Solidification
git pull origin main
```

Validate B7 and C7 before rerunning the full matrix.

Check that the block is present:

```bash
grep -n "solidificationMeltingMomentumDiagnostics" \
  cases_controlled_buoyancy/B7_outer4/system/researchDiagnostics

grep -n "solidificationMeltingMomentumDiagnostics" \
  cases_controlled_buoyancy/C7_outer4/system/researchDiagnostics
```

During the run, inspect:

```bash
grep "solidificationMelting diagnostics" log.foamMultiRun
```

After a valid write, the `metal` time directories should contain fields including:

```text
phaseChangeDarcyCoeff
phaseChangeDarcyAcceleration
phaseChangeBuoyancyAcceleration
pRghAcceleration
phaseChangeDragToBuoyancy
phaseChangeDragToPressure
```

Quick interpretation:

- `phaseChangeDarcyCoeff` [1/s]: local mushy-zone damping strength.
- `magPhaseChangeDarcyAcceleration` [m/s²]: Darcy deceleration magnitude.
- `magPhaseChangeBuoyancyAcceleration` [m/s²]: local model buoyancy acceleration.
- `magPRghAcceleration` [m/s²]: acceleration scale associated with the `p_rgh` gradient.
- `phaseChangeDragToBuoyancy`: Darcy-damping to buoyancy ratio.
- `phaseChangeDragToPressure`: Darcy-damping to pressure-gradient ratio.

Do not interpret very large ratios near nearly-zero denominators in isolation; inspect the absolute magnitudes and liquid fraction as well.
